# Bizhub Payment Gateway

เกตเวย์รับชำระเงินแบบหลายร้านค้า (multi-merchant) ร้านค้าเชื่อมต่อผ่าน API แล้วส่งลูกค้าไปจ่ายที่หน้าชำระเงินของเกตเวย์

| ช่องทาง | วิธีทำงาน | ใครยืนยันยอด |
|---|---|---|
| **PromptPay QR** | สร้าง QR ตามยอดเงิน (มาตรฐาน EMVCo / Thai QR) เงินเข้าพร้อมเพย์ของร้านโดยตรง ลูกค้าแนบสลิปหลังโอน | **อัตโนมัติ** ตรวจสลิปกับธนาคาร |
| **บัตรเครดิต/เดบิต** | ข้อมูลบัตรถูกแปลงเป็น token ในเบราว์เซอร์ แล้วตัดเงินผ่าน Omise (Opn Payments) รองรับ 3-D Secure | อัตโนมัติจากผู้ให้บริการบัตร |
| **โอนเงิน + แนบสลิป** | แสดงเลขบัญชีร้าน ลูกค้าโอนแล้วอัปโหลดสลิป | **อัตโนมัติ** ตรวจสลิปกับธนาคาร |

ทุกการเปลี่ยนสถานะจะส่ง **webhook ที่เซ็นด้วย HMAC-SHA256** ไปยังร้านค้า พร้อม retry อัตโนมัติ

## เริ่มใช้งาน

ต้องใช้ Node.js 22.13 ขึ้นไป (ใช้ SQLite ที่มากับ Node ไม่ต้องติดตั้งฐานข้อมูลเพิ่ม)

```bash
npm install
cp .env.example .env        # แก้ ADMIN_TOKEN ให้เป็นค่าสุ่มยาว ๆ
export $(grep -v '^#' .env | xargs)
npm run dev                 # http://localhost:3000
npm test                    # รันชุดทดสอบ
```

### ตั้งค่าครั้งแรก

1. สร้างบัญชีแอดมินคนแรก: `npm run create-admin -- --email you@example.com --name "ชื่อคุณ"`
   (หรือเปิด `/admin/console` แล้วเลือก "เข้าด้วย ADMIN_TOKEN" เพื่อสร้างบัญชีจากหน้าเว็บ)
2. เข้า `/admin/console` → เมนู **ร้านค้า** → **+ เพิ่มร้านค้า** กรอกข้อมูลร้านและอีเมลเจ้าของร้าน
3. ระบบแสดง API key และรหัสผ่านชั่วคราวของเจ้าของร้าน**ครั้งเดียว** ให้ส่งให้ร้านค้าทางช่องทางที่ปลอดภัย
4. เจ้าของร้านเข้า `/dashboard` ตั้งรหัสผ่านใหม่ แล้วเพิ่มบัญชีพนักงานเองได้

### สร้างร้านค้าผ่าน API

```bash
curl -X POST http://localhost:3000/admin/merchants \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name": "ร้านกาแฟบ้านสวน",
    "promptpay_id": "0812345678",
    "bank_name": "กสิกรไทย",
    "bank_account_no": "123-4-56789-0",
    "bank_account_name": "บจก. บ้านสวน",
    "webhook_url": "https://shop.example.com/webhooks/bizhub"
  }'
```

ผลลัพธ์จะมี `test_secret_key`, `live_secret_key` และ `webhook_secret` ซึ่ง**แสดงครั้งเดียว** ให้ส่งให้ร้านค้าเก็บไว้
(หรือใช้ `npm run create-merchant -- --name "..." --promptpay 0812345678`)

## ติดตั้งใช้งานจริง (Docker + HTTPS อัตโนมัติ)

ต้องมีเซิร์ฟเวอร์ Linux ที่ติดตั้ง Docker แล้ว (cloud เจ้าไหนก็ได้ หรือเครื่องของบริษัท) และโดเมนที่ชี้ DNS (A record) มาที่เครื่องนั้น

```bash
git clone <repo> && cd Bizhub-Payment-Gateway-
cp .env.example .env          # ตั้ง DOMAIN, ADMIN_TOKEN (สุ่มยาว ๆ) และค่าอื่นที่ต้องใช้
docker compose up -d --build  # Caddy ขอใบรับรอง HTTPS ให้เองภายในไม่กี่นาที
docker compose exec gateway node --import tsx scripts/create-admin.ts --email you@company.com --name "ชื่อคุณ"
```

แล้วเปิด `https://<โดเมน>/admin/console` เพื่อสร้างร้าน (บริษัทของคุณ) และบัญชีเจ้าของ

หรือใช้สคริปต์ติดตั้งครั้งแรก ซึ่งติดตั้ง Docker ตรวจว่า DNS ชี้มาถูกเครื่อง สร้าง `.env` พร้อมรหัสลับแบบสุ่ม เปิดระบบ และสร้างบัญชีแอดมินให้ในคำสั่งเดียว:

```bash
sudo bash scripts/setup-server.sh pay.bizhubpay.com you@company.com "ชื่อคุณ"
```

- **ข้อมูลทั้งหมด** (ฐานข้อมูล, รูปสลิป, ไฟล์สำรอง) อยู่ใน volume `gateway-data` อัปเดตเวอร์ชันด้วย `git pull && docker compose up -d --build` โดยข้อมูลไม่หาย
- **สำรองข้อมูลอัตโนมัติ** ทุก `BACKUP_INTERVAL_HOURS` ชั่วโมง (ค่าเริ่มต้น 24) ไว้ที่ `/data/backups` เก็บ `BACKUP_KEEP` ไฟล์ล่าสุด
- **สำรองนอกเครื่อง:** ตั้ง `BACKUP_S3_*` แล้วระบบจะส่งไฟล์สำรองฐานข้อมูลและรูปสลิปใหม่ ๆ ไปเก็บใน bucket แบบ S3
  (AWS S3, Cloudflare R2, DigitalOcean Spaces, MinIO) ถ้าส่งไม่สำเร็จจะลองใหม่รอบถัดไปและบันทึกใน log
- **PDPA:** ทุกหน้าที่ลูกค้าแนบสลิปจะแจ้งว่าใช้ข้อมูลอะไร เพื่ออะไร พร้อมลิงก์นโยบายของร้าน (ตั้งใน Dashboard → ตั้งค่า)
  และหน้านโยบายของระบบที่ `/privacy` (ตั้งชื่อผู้ให้บริการด้วย `OPERATOR_NAME`, `OPERATOR_CONTACT`)
- **ระยะเวลาเก็บสลิป (PDPA):** ตั้ง `SLIP_RETENTION_DAYS` เพื่อลบรูปสลิปของรายการที่ปิดแล้วเมื่อเกินกำหนด เลขอ้างอิงธนาคารยังเก็บไว้ จึงยังกันสลิปซ้ำได้
  ค่าเริ่มต้นคือ 0 (เก็บไว้ตลอด) ให้กำหนดร่วมกับฝ่ายบัญชีว่าต้องเก็บหลักฐานนานเท่าไร

## ใช้แทนการรับโอนแบบแมนนวล

ถ้าตอนนี้ลูกค้าโอนเข้าเลขบัญชีแล้วส่งสลิปให้พนักงานเช็กเอง:

1. เจ้าของร้านเปิด **หน้าแจ้งชำระเงิน** ที่ Dashboard → บัญชีธนาคาร จะได้ลิงก์ถาวร `https://<โดเมน>/notice/<รหัสร้าน>` และ QR สำหรับพิมพ์ในบิล
2. ส่งลิงก์ให้ลูกค้าทาง LINE หรือปักหมุดใน LINE OA ลูกค้าโอนเข้าเลขบัญชีเหมือนเดิม แล้วกรอกยอด เลขบิล และแนบสลิป
3. ระบบตรวจสลิปกับธนาคาร (เมื่อตั้ง `SLIP_VERIFIER`) แล้วบันทึกเข้ารายการชำระเงินโดยใช้เลขบิลที่ลูกค้ากรอกเป็นเลขอ้างอิง
   - ตรวจผ่าน: ลูกค้าเห็น "ได้รับเงินแล้ว" ทันที
   - ตรวจไม่ผ่าน: ลูกค้าเห็นเหตุผล และไม่มีรายการค้างในระบบ
   - ตรวจเองไม่ได้: เข้าคิว "รอตรวจสอบ" ให้พนักงาน
4. บิลที่อยากให้จ่ายตรงยอด ใช้ **สร้างลิงก์ชำระเงิน** แทน (ได้ QR PromptPay ตามยอด)

หน้าแจ้งชำระเงินจำกัด 10 ครั้งต่อชั่วโมงต่อผู้ใช้ เพื่อไม่ให้ถูกใช้เปลืองโควต้าตรวจสลิป

## ยืนยันสลิปอัตโนมัติ

เมื่อลูกค้าแนบสลิป ระบบส่งภาพไปให้ผู้ให้บริการตรวจสลิป ([EasySlip](https://easyslip.com) หรือ [SlipOK](https://slipok.com))
อ่าน QR บนสลิปแล้วเช็กกับเครือข่ายธนาคารว่ารายการโอนมีอยู่จริง จากนั้นเกตเวย์ตรวจซ้ำเองทุกข้อก่อนตัดสินว่าจ่ายแล้ว:

| ตรวจ | ไม่ผ่านแล้วเกิดอะไร |
|---|---|
| รายการโอนมีอยู่จริงที่ธนาคาร (กันสลิปปลอม/ตัดต่อ) | ปฏิเสธ ลูกค้าแนบใหม่ได้ |
| ยอดเงินตรงกับยอดที่ต้องชำระ | ยอดขาด → ปฏิเสธ · ยอดเกิน → ส่งให้ร้านค้าตรวจ |
| บัญชีผู้รับเป็นของร้านนี้ (เทียบพร้อมเพย์/เลขบัญชีที่ธนาคารปิดบางหลัก) | ไม่ตรง → ปฏิเสธ · อ่านไม่ได้ → ส่งให้ร้านค้าตรวจ |
| เวลาโอนไม่เก่ากว่าตอนสร้างรายการ (กันเอาสลิปเก่ามาใช้) | ปฏิเสธ |
| สลิปนี้ยังไม่เคยใช้จ่ายรายการอื่น (ทุกร้านในเกตเวย์) | ปฏิเสธ |

ผลลัพธ์มี 3 แบบ:

- **verified**: รายการเป็น `succeeded` ทันที ลูกค้าเห็น "ชำระเงินสำเร็จ" ภายในไม่กี่วินาที และร้านค้าได้ webhook `payment.succeeded`
- **rejected**: รายการยังเป็น `pending` ลูกค้าเห็นเหตุผลเป็นภาษาไทยแล้วแนบใหม่ได้ (ไม่เกิน 5 ครั้งต่อรายการ) ร้านค้าได้ webhook `payment.slip_rejected`
- **needs_review**: เช่น ธนาคารยังไม่อัปเดตรายการ หรือผู้ให้บริการล่ม รายการจะเป็น `awaiting_review` และระบบลองตรวจซ้ำเองเป็นระยะ (สูงสุด 6 ครั้งใน ~4 ชั่วโมง) ถ้ายังตัดสินไม่ได้ ร้านค้า approve/reject เองได้

ตั้งค่าใน `.env`:

```bash
SLIP_VERIFIER=easyslip          # หรือ slipok
EASYSLIP_API_KEY=...            # ถ้าใช้ EasySlip
SLIPOK_BRANCH_ID=... SLIPOK_API_KEY=...   # ถ้าใช้ SlipOK
```

- โหมดทดสอบ (`sk_test_`) ใช้ตัวจำลองเสมอ ภาพใดก็ผ่านด้วยยอดที่ถูกต้อง จึงลองทั้ง flow ได้โดยไม่เสียโควต้า
- ถ้ายังไม่ตั้งค่าผู้ให้บริการ สลิปโหมด live จะรอร้านค้ายืนยันเองเหมือนเดิม
- สลิปไฟล์ PDF ตรวจอัตโนมัติไม่ได้ ระบบจะส่งให้ร้านค้าตรวจ
- ประวัติการตรวจทุกครั้งดูได้ที่ `GET /v1/payments/:id/slip-checks`

## เชื่อมบัญชีธนาคาร (ยืนยันเงินเข้าโดยไม่ต้องใช้สลิป)

เจ้าของร้านเชื่อมบัญชีได้ที่ Dashboard → **บัญชีธนาคาร** (แยกโหมดจริง/ทดสอบ) แล้วได้ **URL รับแจ้งเงินเข้า** และ**รหัสลับ**
ให้นำไปตั้งค่าที่ธนาคาร หรือระบบตัวกลางที่ส่งต่อแจ้งเตือนยอดเข้า ทุกครั้งที่มีเงินเข้า ระบบจะจับคู่กับรายการและยืนยันให้ทันที

| ร้านมี | QR ที่ลูกค้าสแกน | วิธีจับคู่ |
|---|---|---|
| **Biller ID** (สมัครบริการรับชำระผ่าน QR กับธนาคาร) | Thai QR แบบ bill payment ที่ฝัง**รหัสชำระเงิน**ของรายการไว้เป็น Reference 1 | ตรงรหัส แม่นยำ 100% |
| ไม่มี Biller ID | PromptPay ปกติ | ยอดเงินตรงกับรายการที่รอชำระ**เพียงรายการเดียว**ในช่วงเวลานั้น |

- ยอดไม่ตรงจะส่งให้ร้านตรวจ (`awaiting_review`); เงินเข้าหลังรายการปิด, ไม่มีรายการให้จับคู่ หรือมีหลายรายการยอดเท่ากัน
  จะถูกบันทึกไว้โดยไม่เปลี่ยนรายการใด ๆ และพนักงานกด **จับคู่กับรายการ** เองได้
- แจ้งซ้ำไม่นับซ้ำ (ดูจาก `trans_ref`); เงินเข้าก้อนเดียวกันใช้เป็นสลิปจ่ายอีกรายการไม่ได้ (ใช้ตารางเดียวกับระบบตรวจสลิป)
- รายการที่ยืนยันแล้วแสดง "ยืนยันโดย: แจ้งเตือนเงินเข้าจากธนาคาร" และส่ง webhook `payment.succeeded` ตามปกติ
- โหมดทดสอบมีปุ่ม **จำลองเงินเข้า** ให้ลองได้โดยไม่ต้องมีธนาคาร

รูปแบบแจ้งเตือนที่ธนาคาร/ตัวกลางต้องส่ง (1 คำขอต่อ 1 รายการเงินเข้า):

```http
POST /bank/notify/<connection id>
Content-Type: application/json
Bizhub-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(รหัสลับ, "<t>.<raw body>")>

{ "trans_ref": "015302134501ATF02345", "amount": "185.00", "paid_at": "2026-10-29T14:57:00+07:00",
  "ref1": "3BDZC36Q9T", "payer_name": "นางสาว สมใจ ใจดี" }
```

ตอบกลับ `{"outcome": "matched" | "duplicate" | "amount_mismatch" | "already_paid" | "paid_after_close" | "ambiguous" | "unmatched", ...}`
ลายเซ็นผิดหรือเก่ากว่า 5 นาทีจะได้ 401

> **ข้อจำกัดตามจริง:** ในไทยยังไม่มีบริการกลางให้ระบบภายนอกอ่านยอดเข้าบัญชีของร้านได้เอง ข้อมูลต้องมาจากธนาคารที่ร้านทำสัญญาไว้
> (เช่น บริการ QR payment / API แจ้งยอดเข้าของ KBank, SCB, กรุงเทพ) หรือระบบตัวกลางที่ร้านใช้ เกตเวย์จึงมีช่องทางรับแจ้งเตือนที่มาตรฐาน
> และปลอดภัยไว้ให้ ส่วนการต่อกับ API ของแต่ละธนาคารโดยตรงจะทำได้เมื่อร้านได้เอกสารและสิทธิ์จากธนาคารนั้น

## ร้านค้าสมัครเอง + ยืนยันตัวตน (KYC)

เปิดด้วย `SIGNUP_ENABLED=true` (ช่วงใช้ภายในบริษัทให้ปิดไว้)

1. ร้านสมัครที่ `/signup` เข้า Dashboard ได้ทันที**ในโหมดทดสอบ** (ลองสร้างลิงก์ จำลองเงินเข้า ใช้ API key โหมดทดสอบได้)
2. เจ้าของร้านกรอกข้อมูลที่เมนู **เปิดรับเงินจริง**: ประเภทผู้ประกอบการ, เลขผู้เสียภาษี/บัตรประชาชน, ผู้ติดต่อ, บัญชีรับเงิน
   และแนบเอกสาร (บัตรประชาชน, หน้าสมุดบัญชี และหนังสือรับรองบริษัทถ้าเป็นนิติบุคคล) แล้วกด **ส่งตรวจ**
3. แอดมินตรวจที่ Admin Console → **คำขอเปิดร้าน** แล้ว **อนุมัติ** หรือ**ไม่อนุมัติ** (ต้องระบุเหตุผล ร้านเห็นและแก้ไขส่งใหม่ได้)
4. เมื่ออนุมัติ โหมดใช้งานจริงและ live API key จะเปิดใช้ได้ทันที

กติกาความปลอดภัย:
- ก่อนอนุมัติ: live key, การสลับไปโหมดจริง และหน้าแจ้งชำระเงินถูกปิดทั้งหมด
- หลังอนุมัติ: บัญชีรับเงินแก้ได้โดยแอดมินเท่านั้น กันบัญชีร้านถูกเจาะแล้วถูกเปลี่ยนปลายทางเงิน
- ร้านที่แอดมินสร้างเองถือว่าอนุมัติแล้ว
- การเปิดดูเอกสารของแอดมินทุกครั้งถูกบันทึกในประวัติการใช้งาน

## ค่าบริการร้านค้า (แพ็กเกจแบบผสม)

ใช้เก็บค่าบริการจากร้านค้าที่ใช้ระบบ (เมื่อขายเป็นสินค้า) ราคาไม่ได้ฝังในโค้ด แอดมินตั้งเองที่เมนู **แพ็กเกจและบิล**

- **แพ็กเกจ** = ค่ารายเดือน + จำนวนรายการที่รวมไว้ + ค่าธรรมเนียมต่อรายการที่เกิน + % ของยอดรับชำระ (ใส่ 0 ได้ทุกช่อง) เช่น Starter ฿490/เดือน รวม 300 รายการ เกินคิด ฿2/รายการ
- นับเฉพาะรายการ**โหมดจริงที่ชำระสำเร็จ**ในเดือนนั้น (ตามเวลาไทย) รายการทดสอบไม่คิดเงิน
- **วันที่ 1 ของทุกเดือน** ระบบออกใบแจ้งหนี้ของเดือนก่อนให้ทุกร้านที่มีแพ็กเกจและผ่าน KYC แล้ว (กดออกเองได้ที่ปุ่ม "ออกบิลรอบ…") บวก VAT ตาม `VAT_RATE` เลขที่ `INV-YYYYMM-0001` ราคาในใบแจ้งหนี้ถูกบันทึกตายตัว แก้แพ็กเกจภายหลังไม่กระทบบิลเก่า
- **ร้านจ่ายผ่านระบบนี้เอง**: ตั้ง `BILLING_MERCHANT_ID` เป็นรหัสร้านของบริษัทผู้ให้บริการ ใบแจ้งหนี้แต่ละใบจะมีลิงก์ชำระ (QR PromptPay / แนบสลิป) ของร้านนั้น เมื่อชำระสำเร็จ ใบแจ้งหนี้เปลี่ยนเป็น "ชำระแล้ว" อัตโนมัติ ลิงก์หมดอายุจะออกใหม่ให้เมื่อร้านกดชำระ
- ร้านค้าเห็นยอดเดือนปัจจุบัน (ประมาณการ) ใบแจ้งหนี้ และพิมพ์/บันทึก PDF ได้ที่เมนู **ค่าบริการ** (เจ้าของร้าน ผู้จัดการ และฝ่ายบัญชี)
- แอดมินบันทึก "ชำระแล้ว" เองได้เมื่อรับเงินนอกระบบ หรือ "ยกเลิก" ใบที่ออกผิด ทุกการกระทำอยู่ในประวัติการใช้งาน
- เอกสารที่ออกเป็น **ใบแจ้งหนี้** ไม่ใช่ใบกำกับภาษี หากบริษัทจดทะเบียน VAT ให้ออกใบกำกับภาษีจากระบบบัญชีของบริษัทตามเดิม

### ยืนยันตัวตน 2 ชั้น (2FA)

- ทุกบัญชี (พนักงานร้านและแอดมิน) เปิดใช้ได้ที่หน้า **ตั้งค่า / บัญชีของฉัน** ด้วยแอป Authenticator (Google / Microsoft Authenticator ฯลฯ)
- เมื่อเปิดใช้ ล็อกอินต้องกรอกรหัส 6 หลักต่อจากรหัสผ่าน; ได้**รหัสกู้คืน 10 รหัส** (ใช้ได้รหัสละครั้ง) ไว้ใช้ตอนทำมือถือหาย
- **บังคับใช้:** เจ้าของร้านติ๊ก "บังคับให้พนักงานทุกคนใช้ 2FA" ที่หน้าพนักงาน (แอดมินตั้งให้ร้านได้ด้วย);
  ฝั่งแอดมินตั้ง `ADMIN_REQUIRE_2FA=true` ใน `.env` — คนที่ยังไม่ตั้งค่าจะใช้งานอื่นไม่ได้จนกว่าจะตั้งค่าเสร็จ
- **ทำมือถือหาย:** ใช้รหัสกู้คืน หรือให้ผู้จัดการบัญชีกด **ล้าง 2FA** (ผู้ใช้ถูกออกจากระบบและต้องตั้งค่าใหม่)
- กันการใช้รหัสเดิมซ้ำ, ใส่รหัสผิด 5 ครั้งล็อก 15 นาที, ทุกการเปิด/ปิด/ล้าง/ใช้รหัสกู้คืนถูกบันทึกในประวัติการใช้งาน
- การเข้าด้วย Secret key หรือ `ADMIN_TOKEN` ไม่ผ่าน 2FA (เป็นความลับระดับระบบอยู่แล้ว) จึงควรเก็บให้ดีและใช้บัญชีส่วนตัวเป็นหลัก

### ความปลอดภัยของบัญชี

- รหัสผ่านเก็บแบบ scrypt; บัญชีใหม่และการรีเซ็ตได้**รหัสผ่านชั่วคราว**ที่ต้องเปลี่ยนก่อนใช้งาน (อย่างน้อย 10 ตัว มีทั้งตัวอักษรและตัวเลข)
- ใส่รหัสผิด 5 ครั้งใน 15 นาที บัญชีนั้นจะถูกล็อกชั่วคราว (นับแยกตามอีเมล + IP)
- เบราว์เซอร์ถือเพียง session cookie แบบ HttpOnly + SameSite=Strict อายุ 12 ชั่วโมง; ปิดบัญชีหรือรีเซ็ตรหัสผ่านจะออกจากระบบทุกอุปกรณ์ทันที
- ระบบกันไม่ให้ปิดหรือลดบทบาทเจ้าของร้าน/ผู้ดูแลสูงสุดคนสุดท้าย
- หน้าเว็บใช้ Content-Security-Policy แบบเข้ม (สคริปต์จากเซิร์ฟเวอร์เท่านั้น)

## API สำหรับร้านค้า

ยืนยันตัวตนด้วย `Authorization: Bearer sk_test_...` (ทดสอบ) หรือ `sk_live_...` (ใช้งานจริง) ข้อมูลทดสอบกับข้อมูลจริงแยกจากกันเด็ดขาด
จำนวนเงินเป็น **สตางค์** เสมอ (`25000` = 250.00 บาท)

### สร้างรายการชำระเงิน

```bash
curl -X POST http://localhost:3000/v1/payments \
  -H "Authorization: Bearer sk_test_..." -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1001" \
  -d '{"amount": 25000, "method": "promptpay", "reference": "INV-1001",
       "description": "ลาเต้เย็น x2", "return_url": "https://shop.example.com/thanks"}'
```

```json
{
  "id": "pay_h0ZFryINk0eHB7Aw1aW3CRXA",
  "status": "pending",
  "amount": 25000,
  "method": "promptpay",
  "checkout_url": "http://localhost:3000/checkout/pay_h0ZF...",
  "promptpay": { "payload": "000201010212...", "qr_image_url": ".../qr.png" },
  "expires_at": "2026-10-27T10:15:00.000Z"
}
```

ส่งลูกค้าไปที่ `checkout_url` หรือจะนำ `promptpay.payload` ไปสร้าง QR ในแอปตัวเองก็ได้
เมื่อจบรายการ หน้าชำระเงินจะพาลูกค้ากลับไปที่ `return_url?payment_id=...&status=...`
(อย่าเชื่อพารามิเตอร์นี้อย่างเดียว ให้ยืนยันจาก webhook หรือ `GET /v1/payments/:id`)

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| `POST` | `/v1/payments` | สร้างรายการ (`method`: `promptpay` / `card` / `bank_transfer`, `expires_in` เป็นวินาที) |
| `GET` | `/v1/payments` | รายการทั้งหมด (`status`, `reference`, `limit`, `starting_after`) |
| `GET` | `/v1/payments/:id` | ดูรายการ |
| `POST` | `/v1/payments/:id/approve` | ยืนยันด้วยมือ (กรณีระบบส่งให้ตรวจ) |
| `POST` | `/v1/payments/:id/reject` | ปฏิเสธสลิป `{"reason": "amount_mismatch"}` |
| `GET` | `/v1/payments/:id/slip` | ดาวน์โหลดสลิปที่ลูกค้าแนบ |
| `GET` | `/v1/payments/:id/slip-checks` | ประวัติการตรวจสลิปอัตโนมัติ |
| `POST` | `/v1/payments/:id/cancel` | ยกเลิกรายการที่ยังไม่จ่าย |
| `POST` | `/v1/payments/:id/simulate` | (เฉพาะ test key) จำลองผล `{"status": "succeeded"}` |
| `GET` | `/v1/merchant` | ข้อมูลร้าน + `webhook_secret` |

### สถานะ

```
pending ──(สลิปผ่าน / บัตรผ่าน)──▶ succeeded
   │──(สลิปไม่ผ่าน)──▶ pending (แนบใหม่ได้)
   ├──(ตรวจยังไม่ได้)──▶ awaiting_review ──(ตรวจซ้ำผ่าน / approve)──▶ succeeded
   │                              └──────reject─────▶ failed
   ├──(เลยเวลา)──▶ expired
   └──(cancel)──▶ cancelled
```

บัตรที่ถูกปฏิเสธจะยังคงเป็น `pending` (เก็บเหตุผลไว้ใน `failure_reason`) ให้ลูกค้าลองบัตรใบอื่นได้จนกว่าจะหมดเวลา

## Webhook

เหตุการณ์: `payment.created`, `payment.awaiting_review`, `payment.slip_rejected`, `payment.succeeded`, `payment.failed`, `payment.expired`, `payment.cancelled`

```json
{ "id": "evt_...", "object": "event", "type": "payment.succeeded", "created_at": "...", "data": { "...": "payment" } }
```

ทุกคำขอมี header `Bizhub-Signature: t=<unix>,v1=<hex>` โดย `v1 = HMAC_SHA256(webhook_secret, "<t>.<raw body>")`
ร้านค้าต้องตอบ 2xx ภายใน 10 วินาที ไม่เช่นนั้นระบบจะส่งใหม่ที่ 1 นาที, 5 นาที, 30 นาที, 2, 6, 12 และ 24 ชั่วโมง

ตัวอย่างการตรวจลายเซ็น (Node.js):

```js
import crypto from "node:crypto";

function verify(rawBody, header, secret, toleranceSec = 300) {
  const { t, v1 } = Object.fromEntries(header.split(",").map((p) => p.split("=")));
  if (Math.abs(Date.now() / 1000 - Number(t)) > toleranceSec) return false;
  const expected = crypto.createHmac("sha256", secret).update(`${t}.${rawBody}`).digest("hex");
  return expected.length === v1.length && crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(v1));
}
```

webhook อาจถูกส่งซ้ำได้ ให้ใช้ `id` ของ event กันการประมวลผลซ้ำ

## บัตรเครดิต

- **โหมดทดสอบ** ไม่ต้องตั้งค่าอะไร: `4242 4242 4242 4242` = สำเร็จ, `4000 0000 0000 0002` = ถูกปฏิเสธ
- **โหมดจริง** ตั้ง `OMISE_PUBLIC_KEY` และ `OMISE_SECRET_KEY` จากบัญชี Opn Payments
  หน้าชำระเงินใช้ Omise.js แปลงบัตรเป็น token ในเบราว์เซอร์ เกตเวย์จึงไม่เคยเห็นเลขบัตร
- ผู้ให้บริการอื่น (2C2P, GB Prime Pay, Stripe) เพิ่มได้โดยเขียนคลาสตาม `CardProvider` ใน `src/providers/card.ts`

## ก่อนขึ้นระบบจริง

- รันหลัง HTTPS (reverse proxy เช่น Nginx/Caddy) และตั้ง `PUBLIC_BASE_URL` เป็นโดเมนจริง
- สำรองโฟลเดอร์ `DATA_DIR` (ฐานข้อมูล + สลิป) สม่ำเสมอ ถ้าปริมาณสูงควรย้ายไป PostgreSQL และเก็บสลิปบน object storage
- ใส่ rate limit สำหรับ `/checkout/*` ที่ reverse proxy
- สมัครผู้ให้บริการตรวจสลิปและตั้ง `SLIP_VERIFIER` เพื่อเปิดการยืนยันอัตโนมัติในโหมด live
- ลูกค้าที่จ่าย PromptPay แล้วไม่แนบสลิป ระบบจะยังไม่รู้ว่าจ่ายแล้ว ถ้าต้องการยืนยันโดยไม่ต้องใช้สลิปเลย ต้องใช้ API แจ้งยอดเข้าของธนาคาร (เช่น KBank / SCB Open API) ซึ่งต้องทำสัญญากับธนาคาร
- การรับเงินแทนร้านค้า (พักเงินไว้ที่เกตเวย์) อาจต้องได้รับอนุญาตจาก ธปท. ระบบนี้จึงออกแบบให้เงินเข้าบัญชีร้านค้าโดยตรง
